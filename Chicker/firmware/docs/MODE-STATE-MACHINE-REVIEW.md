## Message handling (element 7): full description, for the chart later

Henry's chart has one box for this, "message handling according to #7". This section is what that box means,
written so it can be drawn later. The behaviour is agreed (element 7, MSG-1, MSG-2).

### Where it applies

Every CAN frame goes through the message handler, **whatever state the mode machine is in**. What the handler
may do depends on the state:

* **Wait for Bat, Start BKBM interrupt, Locked:** heartbeat frames are handled (timer refreshed, STATUS sent).
  Commands are **not acted on** and not saved for later (Locked: STATUS carries the fault flag).
* **Every other state** (Wait for Message, Arm Kick, Charge Hold, the damp loop, ...): commands are acted on, as
  below. A good command interrupts whatever the machine was doing (one exception: renew).

### Step by step (each line is one box or arrow to draw)

```
 1. CAN frame received
 2. ├─ heartbeat frame      → refresh the heartbeat timer, send STATUS → back to the current state
 3. ├─ not for the chicker  → ignore → back to the current state
 4. ├─ bad command          → Unknown command (count it, log it; reject message if the team wants, T-2)
 5. │                         → back to the current state (nothing changes, nothing de-armed)
 6. └─ good command         → (Wait for Bat / Start BKBM / Locked: ignore → back to the current state)
 7.                         → de-arm kick (except a DAMP renew, line 13)
 8.                         → Command Received
 9.  Command Received
10.  ├─ MODE_IDLE                       → Set Idle Mode (chg_stop = 1, stop PWM) → Wait for Message
11.  ├─ MODE_CHG                        → de-arm kick / stop PWM → Enable Charging → Wait for Message
12.  ├─ MODE_AUTOKICK && PWM running    → Arm Kick → set mode back to MODE_DAMP → damp loop Wait   (element 18)
13.  ├─ MODE_DAMP && PWM running        → Renew Damp start variable (kick stays armed) → damp loop Wait  (element 17)
14.  ├─ MODE_AUTOKICK && PWM not running → Enable Charging → [last kick >= KICK_MIN_INTERVAL_MS] → Arm Kick → ...  (elements 9–12)
15.  └─ MODE_DAMP && PWM not running    → Enable Charging → [last kick >= KICK_MIN_INTERVAL_MS && HV >= 180] → Charge Hold → ...  (elements 14–16)
```

### Definitions used above

| Term | Meaning |
|---|---|
| Heartbeat frame | The Pi's 5 Hz heartbeat. Never de-arms, never goes to Command Received. Any valid frame from the Pi refreshes the heartbeat timer. |
| Good command | Known command CAN ID, correct data length, every value in range (known mode, kick PW 100–5000 µs, damp parameters within limits). |
| Bad command | Anything for the chicker that isn't a good command. |
| PWM running | Flag: on at Start Damping PWM, off at every Stop PWM. Not the same as `mode == MODE_DAMP`. |
| Order | Good commands are handled one at a time, in the order they arrived; none are dropped. |

### Who stops the PWM

Every way out of a damp stops the PWM: the damp loop's own exits (timeout / max hold, elements 16, 19, 20),
MODE_IDLE (Set Idle Mode), MODE_CHG, heartbeat loss and battery loss. MODE_DAMP renews, MODE_AUTOKICK keeps it
running until the kick. Below the state machine, the kicker driver never runs the PWM longer than
`DAMP_MAX_TOTAL_MS` (backstop for code bugs, not a state).

## Notes

| # | Note |
|---|---|
| HB-1 | **Heartbeat details.** The Pi sends at 5 Hz, so the 5 s timeout means ~25 frames in a row must be missed before communication counts as lost. Dropped packets never trip it; only a real outage does. Loss detection is a single timestamp ("last valid frame from the Pi"), not a miss counter. **Early warning (diagnostics only, behaviour unchanged):** after ~1 s without a frame, set a "heartbeat late" flag in STATUS and the board log. **Sequence counter:** the board logs gaps and duplicates to measure packet loss but never acts on them. **During the 5 s before loss is declared** the board carries on as normal: an armed kick stays armed (there is no arm timeout on the chart) and a damp ends at its timeout. **After loss** (element 4) the board goes back through Start BKBM interrupt, which waits for a fresh heartbeat before Idle. |
| HB-2 | **Heartbeat loss (element 4).** *Dump:* dumping on heartbeat loss is the intended behaviour (Henry). *Armed kick:* de-armed (`armed = 0`), so the break-beam interrupt (still attached) can't fire a kick. The bank is dumping anyway (a full dump takes ~7 s, Henry's measurement), so a kick after loss would get weaker quickly. *Damp:* the PWM is stopped on loss, so it can't be left running after the board leaves the damp loop (where its timeout is checked). *Recovery:* Start BKBM interrupt waits for a heartbeat, then Set Idle Mode. |
| MSG-1 | **Message handling (element 7): what counts and why.** <br>• *Heartbeats don't count:* at 5 Hz they would de-arm the kick every 200 ms, so AUTOKICK could never stay armed. <br>• *De-arm on a good message:* Henry added it so an armed kick or a running PWM can't stay active while the board does something else, and so a spammed kick stops the active kick and tries again. Heartbeat loss (element 4) and battery loss (element 1) also de-arm. A corrupt frame just can't cancel an armed kick any more. <br>• *No software checksum:* the CAN hardware already checks a CRC on every frame. <br>• **Team check:** the chicker's CAN IDs (commands, heartbeat, STATUS) must not conflict with other boards (T-1). <br>• **Team decision:** reject messages with a reason code on the bus, or only a reject counter in STATUS / the log (T-2). |
| MSG-2 | **Message handling (element 7): order, repeats, damp, spam.** <br>• *In order, nothing dropped:* the AI isn't expected to send two commands at once, so processing every good command in arrival order is simplest and can't lose a different command. The MCP2515 holds 2 received frames; an overflow is counted in STATUS. <br>• *Repeats are not ignored* (Henry: damping reuses the same commands; ignoring repeats is only worth it if controlled, e.g. with a timer). <br>• *Spammed kicks:* kick commands are allowed as fast as the Pi asks, even on a barely recharged bank (after a miss the robot must kick again quickly). No message rate limit. **But kick pulses must be ≥ `KICK_MIN_INTERVAL_MS` apart** (Henry): two pulses close together, even well over 5 ms apart, combine into one excessively large kick. 500 ms is a starting guess and is probably larger in practice; tune it on the field. Getting it wrong only sends the ball too fast (a foul), it doesn't damage the board. A kick asked for too soon is not dropped: **arming** waits until the interval has passed, then a ball in the beam is kicked straight away (KCK-2). <br>• *Kick during a damp:* see MSG-3. <br>• *A command during a damp:* IDLE / CHG stop the PWM and act on the new command; DAMP renews; AUTOKICK arms inside the damp loop (element 18). <br>• *Why renew:* a robot holding the ball (e.g. lining up a pass) keeps the damp going with no new initial kick and no extra charge → dump cycle. <br>• *Why restart, not add:* like the heartbeat, the hold lasts only while the Pi keeps asking and ends at most one timeout after the last request. Adding time would let spammed commands stack up. <br>• *Why a hard maximum:* whatever the AI does, the PWM can't stay on the solenoid longer than `DAMP_MAX_TOTAL_MS` (from the initial kick, never extended). Not a heating limit (Henry: the hold draws little current; it drains the caps and stops), so 6 s is fine as a backstop. After the damp ends (timeout or maximum), the next DAMP starts a fresh damp. There is no HV floor exit (element 16). <br>• *Pulse in flight:* "stop the active kick" means de-arm the **armed** kick. A pulse already firing (≤ 5 ms) is never cut: cutting it would give a weak partial kick, and the retry has to wait 500 ms anyway. <br>• *Before Idle:* the board runs from the battery, so with no battery it is off unless USB is connected; commands in Wait for Bat realistically only happen on the bench. A command in Start BKBM interrupt still counts for the heartbeat (element 3), but isn't acted on. "Not ready" / "locked" rejects only if the team wants rejects (T-2). <br>• *Spam and the dump resistors:* no longer a risk. Kicks and damps use the hold (no dump), so a spammed AUTOKICK never dumps; only Idle / heartbeat loss dump (coupled C-1). |
| MSG-3 | **Caution, note DMP-5:** the held-out plunger may block the break-beam during a damp. **Kick requested during a damp (element 7). Key change from the chart (Henry).** Example: a damp starts, 1 s passes, a kick is requested. <br>• *The kick request does **not** stop the PWM.* Stopping it then would leave a gap before the ball reaches the break-beam where nothing holds it, and the damp wouldn't work. The kick is queued (armed). <br>• *Case 1, break-beam not tripped yet:* PWM keeps going. When the break-beam trips: **stop the PWM at that moment**, kick, leave the damp. <br>• *Case 1, break-beam never trips:* the damp timeout / `DAMP_MAX_TOTAL_MS` ends the damp; the kick is de-armed with it (Henry). <br>• *Case 2, break-beam already tripped when the kick is requested:* kicked as soon as it is armed. <br>• *Spacing:* `KICK_MIN_INTERVAL_MS` counts from the damp's initial kick, so it is normally already met by the time the ball arrives. <br>• *Plunger position (Henry):* no settle delay needed. The ball pushes the plunger back, so the kick has its stroke when it fires. <br>• *Renew after the kick request (Henry):* keeps the kick armed (element 17), so a kick sent too early still fires. <br>• *How (agreed):* like renew, the AUTOKICK command just sets `armed = 1` and returns to the damp loop's Wait; Wait gets a `kick assigned` exit into the existing GUARD → Kick (elements 18, 19). No new state, and the kick doesn't go through the AUTOKICK states. Going through AUTOKICK would leave the machine in Arm Kick while the PWM runs in the background, with no HV adjustment or timeout: the state wouldn't match the hardware. Break-beam condition widened to include `MODE_DAMP` (element 13). |
| KCK-1 | **Kick HV threshold (element 10).** <br>• *Why the check exists:* Henry added it for the damp → kick case, so a kick isn't fired with no charge. <br>• *Why 100 V, not 180 V:* 180 V blocked a quick re-kick after a miss (the bank is below 180 V) and made HV the main gate on every kick. At 100 V: damp → kick → miss means recharging first (logical); a kick without a miss can still fire straight away. <br>• *Risk accepted:* HV stuck low (≈ 0 V) means the board never kicks. See the charge review open topic (stuck readings). Idea not adopted (Henry: leave as is, change it if it causes problems; the circuit isn't expected to fail): on the normal AUTOKICK path arm on `HV >= 100V \|\| chg_cycle_done`, a new charge-machine flag set on entering Assuming Charged and cleared at New Charge. Plain `done == 0` doesn't work: it is also 0 during a damp, after a dump and after a fault. <br>• *Kick during a damp:* first planned through these AUTOKICK states; settled as arming inside the damp loop (element 18, MSG-3), because the AUTOKICK path would leave the PWM running outside the damp loop. |
| KCK-2 | **Kick spacing vs. ball in the beam: a dilemma (elements 12, 13).** <br>• *Problem:* two kicks closer than `KICK_MIN_INTERVAL_MS` combine into one oversized kick (foul). But if the spacing gates the **fire** step, a ball that is assigned during the interval waits, and may roll away before the kick fires (kick at nothing). Possible later refinement: clear it only if the beam has been OFF longer than a short window (e.g. 100–200 ms, tune on the field). <br>• *Other idea (not adopted):* throttle the kick strength (shorter PW) for a kick inside the interval instead of waiting. | DMP-6 | **Theory: spotting a ball hitting the held plunger from the HV reading (to test once a board works).** <br>• *What happens:* during a hold the charger is off and the dump is off, so the bank only feeds the solenoid (plus the ~1 MΩ divider). Bank current = −C·dV/dt (C = 2 mF): reading HV fast enough gives the solenoid's current for free. When the ball hits, it pushes the plunger back against the magnetic pull: the air gap and the coil's inductance L(x) change quickly, which induces a voltage in the coil (motional EMF ≈ i·dL/dt). For a few ms the coil draws a different current from the bank than in the steady hold, then settles at the new position. The ball's energy goes into the coil circuit: that is the damping. <br>• *Size of the signal (rough):* a 46 g ball at 2 m/s carries ~0.09 J. Absorbed over ~2-5 ms that is ~20-45 W, i.e. a change of ~0.15-0.3 A at 150 V, or a change in dV/dt of ~0.1 V/ms. One ADC count is ~62 mV of bank voltage, so a single 1 kHz reading per loop is not enough; the ADC has to run fast (up to 500 k samples/s, e.g. on the second core or by DMA) and average. Averaging ~100 samples per 0.2 ms brings the noise to a few mV, enough in principle. The exact shape (dip or bump, how long) has to be measured: it depends on the coil, the plunger and the driver. <br>• *Detector:* a running estimate of the bank current (slope of HV over a short window), a slow baseline of that current during the hold, and a trigger when the difference stays beyond a threshold for a few samples. Feeds the mode machine as "ball hit" (in place of the break-beam during a damp: a chart change, to agree later). <br>• *Things that look like a ball and must be told apart:* the duty update every 25 ms (a known current step at a known time: blank the detector around it or subtract it); the Initial Kick and the PWM start; ADC noise; a bouncing ball (several hits). <br>• *Test plan:* (1) log HV at a high rate during holds with no ball: noise and the 25 ms steps; (2) roll / drop the ball at a few known speeds; (3) bouncing balls; (4) compare signal to noise, then pick the threshold and window; (5) check false triggers on long holds with no ball. Needs the RC filter on the HV sense to be fast enough (the simulator assumes 128 µs; check the real value on the schematic). <br>• *If HV is not enough:* a current-sense resistor on the coil sees the inductance directly: in each PWM on-time the current rises at V / L(x), so the plunger position can be read every period (30 kHz); or the reed switch for a simple "plunger pushed back" signal. <br>• *Research and test code:* `to-test/hv-current-sensing/README.md` (sense chain from the schematic, why to look for a voltage step rather than a current spike, a detector checked on synthetic data, a DMA capture + bench script, analysis on the PC, bench test plan). |
